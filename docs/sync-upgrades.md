# Screen-sync upgrade plan

6 November 2026. Baseline Lumen fork `dae70c7`; Lumux source reviewed at `9ee58a8aaad33df61854a69062d2a931fd96b4ec`. This plan distinguishes verified implementation hooks from behavior that still needs implementation and measurement. It does not claim overall superiority without comparative playback tests.

## Evidence and decisions

- [Lumux detector](https://github.com/enginkirmaci/lumux/blob/9ee58a8aaad33df61854a69062d2a931fd96b4ec/src/lumux/black_bar_detector.py) scans mean row/column luminance, checks periodically and interpolates crop coordinates. It uses NumPy. Its integer interpolation can stop short of target boundaries; dark scenes can resemble bars. Lumen will use its existing small raw RGB/RGB0 frames with a separate dependency-free detector, stable candidate timing and exact committed boundaries. No Lumux source is copied.
- Lumen `ScreenCapture.sample` owns sampling, and `queue_mapping` already swaps mapping revisions between frames. This is the verified integration point for crop and later colour processing; GUI and CLI share it.
- Lumen `mapping.resolve` produces normalized rectangles and `mapping.pixels` converts them to capture pixels. Remapping normalized geometry into a detected content rectangle preserves channel ordering/manual overrides without modifying bridge resources.
- Lumux exposes smoothing, brightness, gamma and capture scale in its settings. Lumen already has saturation/gamma processing (`capture.punch`), fixed 64x36 capture and a deadline-paced stream. Later controls must use atomic parameter snapshots rather than additional capture sessions.
- [XDG ScreenCast specification](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.ScreenCast.html) defines source capabilities, source selection and session restoration. Window capture depends on the backend's advertised capabilities; it is not guaranteed on this Hyprland system. Restore tokens must be replaced after use. Lumen already uses SelectSources/Start but has no explicit source-type UI or persistence. This stage needs live backend capability checks before promising window capture.
- Lumen already controls ordinary lights/scenes, but stream cleanup currently only releases the Entertainment area. Restore-on-stop requires explicit state capture, ownership rules and graceful-stop sequencing; it must never restore stale state after another controller takes over.
- Current bridge channel IDs remain authoritative. No upgrade promises extra physical light zones. Existing profiles and manual calibration remain valid.

## Stages and acceptance gates

1. **Automatic black bars and observable sampling (first delivery).** Per mapping profile, add opt-in Ignore black bars, default off for existing profiles. Detect paired horizontal/vertical edge bars, require visible interior and a stable candidate; hold through black frames and temporary one-sided subtitles/overlays. Detection is conservative: dark scene patterns can still be ambiguous, asymmetric borders are deliberately excluded. Minimum content extent 50%, scan at most 5 Hz, require 1 second of stable crop and 0.4 seconds to return to full picture. Apply all channel rectangles inside this picture, including bottom band/inset/manual regions. Send only crop coordinates/effective regions to the UI, never screenshot pixels. Show applied content boundary and effective live regions separately from editable draft geometry. Reset detector on capture/source restart or setting changes. Validate schema, round-trip, old-profile parity, RGB/RGB0, black/dark frames, subtitles, aspect changes, pillarbox/letterbox, edge noise, revision changes, CLI/GUI parity, native UI and bounded runtime cost. Install only after tests and build pass; retain rollback.
2. **Response and colour.** Add response time in milliseconds, output brightness and gamma, with existing saturation retained. Use elapsed-time exponential smoothing (stable across FPS), clamp values and make zero response exactly bypass smoothing. Smooth outgoing channel colours after mapping/colour adjustment; preview must show those actual sent values. Reset history at start/channel-layout change. Test FPS invariance, black output, bounded steps and identity defaults. Verify visible feel with real playback before selecting presets. Controls remain secondary, using current tokens, translations, keyboard access and help.
3. **Preview refinement.** Build on stage 1 telemetry; label detected content versus configured draft, show processing state and useful frame/capture health. No second capture process. Test stale/idle/error state, aspect ratios, narrow window, contrast, translations and modal keyboard behavior. Stage 1 includes the minimum boundary preview needed to verify detection.
4. **Capture options.** Offer explicit portal selection only where supported, preserve working wf-recorder monitor path, and expose a few tested sampling-quality presets rather than arbitrary dimensions. Query AvailableSourceTypes first; fall back visibly when window selection is unsupported. Test cancellation, token rotation, source changes, mapping rounding, CPU/frame freshness and child-process cleanup. No promise of lower CPU or better colour until measured.
5. **Stop behavior.** Default preserve current behavior; offer leave unchanged, restore captured state or apply chosen scene. Capture only affected lights before activation. Restore only after a graceful owned session ends and cleanup succeeds, never on forced termination or detected ownership loss. Test partial failures, offline lights, another controller's changes, stop during startup, repeated stops and quit. UI must expose failures rather than claim restoration succeeded.

Each stage is a separate reviewable change, with automated and real-app checks recorded in verification.md. Stage 1 is the upgrade authorized to start now; later stages remain planned work in this sequence. A full final-build soak and real movie comparisons are release gates for reliability/performance claims, not assumed results.

## First delivery status

Stage 1 implemented and installed: per-profile automatic bars, picture-relative mapping, boundary/effective-region preview and saved CLI/GUI behavior. 54 Python tests, 11 frontend tests, production build, translation parity, dependency audit and an actual 90-second capture/bridge run passed. Detection is enabled for the current saved desk profile; the user's existing 20% inset is retained. Later stages above remain planned, not implemented or claimed verified end-to-end. See verification.md for measurement scope and limits.

## Second delivery status

Stage 2 implemented and installed: shared elapsed-time response, brightness/gamma and retained saturation, accessible controls in a secondary disclosure, atomic persisted parameter snapshots, processed-colour preview, and saved CLI settings/explicit overrides. 67 Python tests, 14 frontend tests, production build, 284-key parity and dependency audit pass. Native live edits, invalid-value rejection, unchanged capture process, pending-save guards and restoration of original preferences passed, with a 60-second runtime check and a 15-second final-build follow-up. Stages 3–5 remain planned. Existing colour behavior is preserved until the user changes the new controls.
